# 011 — Search indexing and SEO

**Area:** How machines find, read and show the site (search engines, link previews, AI crawlers and other readers that aren't a person in a browser): Search Console, sitemap, canonical URLs, page metadata, Open Graph tags, the share image, and what each page says to a reader that doesn't run JavaScript.

## Goal

Get the site indexed by Google: set up Google Search Console, give Google a sitemap, and request indexing. Ranking work comes later (see **Future improvements**).

## What is already there (checked on the live site, 2026-10-17)

- The domain root's `robots.txt` (owned by the org's main Pages site, not this repo) allows all crawlers. Google reads robots.txt only at the domain root, so this repo adds none.
- Every page has its own `<title>`. The homepage has a meta description.
- There is no sitemap and there are no canonical URLs.

## Decisions

- **Sitemap from `app/sitemap.ts`**, generated at build time (works with static export) and served at `/<repo-name>/sitemap.xml`. It lists the fixed pages: home, rankings, compare, how it works, privacy. Video and channel pages (`video/?id=…`) are left out for now.
- **The site's origin comes from an Actions variable**, `NEXT_PUBLIC_SITE_ORIGIN` (e.g. `https://<domain>`). The sitemap needs absolute URLs, and the repo doesn't name the domain (same as `NEXT_PUBLIC_BASE_PATH`, plan 010). If it isn't set (local dev, CI), the build uses `http://localhost:3000`; `deploy.yml` stops if it's missing, so prod never ships localhost URLs.
- **Canonical URL on each fixed page**: `metadataBase` (origin + base path) in the root layout, and `alternates.canonical` per page. This tells Google which address is the real one (e.g. with or without the trailing slash). Paths are root-relative (`/rankings/`), which Next joins to `metadataBase`. Video and channel pages get none: one canonical for all `?id=` URLs would tell Google they're all the same page.
- **Search Console: a URL-prefix property for `https://<domain>/<repo-name>/`**, which covers the site's homepage and every path under it, and nothing else on the domain _(human decision, 2026-10-17: track only this site and all its paths)_. A Domain property can't be limited to a path: it would cover the whole domain and need its DNS. The trailing slash keeps other paths that start with the same letters out. It is https only, which is fine because Pages redirects http to https.
- **Verified with a meta tag**: `metadata.verification.google` in the root layout, with the token from an Actions variable `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`. If it isn't set, no tag is rendered. The token isn't secret; the variable just keeps it out of the code. If the domain's owner ever verifies a Domain property, ours stays as it is.
- **Privacy:** no change. The sitemap and the verification tag load nothing and send no data. Search Console only uses data Google collects by crawling.

### Link previews (2026-10-24)

What a link looks like when pasted into chats and social media (Slack, iMessage, WhatsApp, Discord, LinkedIn, Facebook, X). Today the site has no Open Graph tags and no image, so previews are text only, and some apps show no description.

- **Homepage title:** "HyperStim? How stimulating are the videos your child watches?" _(human decision, 2026-10-24)_. It's also the browser tab and the title in Google's results.
- **Homepage description:** "Discover how stimulating your child’s favorite videos are. Compare thousands of children’s videos based on scene changes, colors, sounds, and more." _(human decision, 2026-10-24)_ (curly apostrophes, as on the rest of the site).
- **Open Graph and Twitter card tags on every page**, from one shared helper in `lib/site.ts`: `og:site_name` "HyperStim?", `og:type` website, `og:url` (the canonical URL), `og:title` / `og:description` (the page's own), `og:image` / `twitter:image` with size and alt text, and `twitter:card` = `summary_large_image`. A helper is needed because Next replaces, not merges, a layout's `openGraph` when a page sets its own. The other pages keep their current titles; their descriptions are under **Page descriptions**.
- **One share image for the whole site**: 1200 × 630 px (the size all the apps above use; they crop to about 1.91:1), opaque PNG (85 KB), committed as `public/og-image.png` and set by the helper. Not Next's `app/opengraph-image.png` convention: with the base path it built the URL with `/<repo-name>/` twice, and pages that set their own `openGraph` lost the image.
  - **Not the logo on its own:** it's 3:1 and transparent, so apps would crop it or put it on black or white unpredictably, and a bare wordmark says little about the site.
  - **The logo above the homepage's kid at the laptop (`kid_1`), on white** _(human decision, 2026-10-24: the homepage's kid; white chosen by me, open to change)_, with margins so square crops (WhatsApp, some X layouts) still show the kid. Composed once with `sharp` and committed; if the art changes, it's recomposed the same way.
- **Privacy:** no change. Apps fetch the page and the image from GitHub Pages like any visitor; nothing is loaded from or sent to anyone new.

### Page descriptions (2026-10-29)

The visible page text stays as it is _(human decision, 2026-10-29)_; the descriptions (shown in search results and link previews, not on the page) carry the parents' words where a parent would search with them. Google bolds matching words in the snippet; descriptions don't affect ranking. "Overstimulating" is phrased as the parent's question, never as a verdict on a video. ### Readers other than people (2026-10-29)

Like screen sizes, the site has several kinds of readers, and each page must make sense to all of them. Most machines read only the page as built (the static HTML), not what JavaScript fills in later. `CLAUDE.md` makes this a requirement for every page.

| Reader | Runs our JavaScript? | What it reads |
|---|---|---|
| People in a browser | Yes | Everything, as designed |
| ↳ screen readers, browser translation, reader mode | Yes | The same page as text: sr-only text, alt text, reading order |
| ↳ JavaScript failed or blocked (bad network, strict blockers) | No | The page as built |
| Link previewers (Slack, iMessage, WhatsApp, Discord, LinkedIn, Facebook, X, Teams, email apps) | No | Only the head: title, description, Open Graph image |
| Search engines (Google, Bing and those built on it, Apple) | Google: yes, later and time-limited; others: partly | The page as built, sometimes the page after JavaScript |
| AI crawlers: training (GPTBot, ClaudeBot, Common Crawl) and live lookups (ChatGPT, Perplexity, Claude fetching a page to answer) | Almost never | The page as built |
| Archives (Wayback Machine) | Partly | The page as built |
| Monitors and SEO tools | No | The page as built and its status code |

- **One page for every reader.** Never detect bots or serve them different content (search engines penalize it as cloaking). Better text for machines goes into the page as built, which everyone gets first.
- **The page as built must read sensibly**: a meaningful title, description and H1, and every loading state a sentence. No placeholder text that only looks right as a gray bar (the home hero's "00,000 videos from 000 channels"), no bare "Loading…" as the only content. Text that only machines and screen readers need goes in `sr-only`, so what people see doesn't change.
- **The dataset's size before the counts arrive:** "thousands of videos from hundreds of channels" (16,375 + 279 videos, 542 channels on 2026-10-29), sr-only next to the skeleton bars; built in plan 013 step 15 _(human decision, 2026-10-29)_. Stays true until about 1,000 channels; revisit then.
- **AI crawlers are allowed**, for training and live lookups _(human decision, 2026-10-29)_. The domain root's `robots.txt` (not in this repo) already allows all crawlers; nothing to change.
- **Crawlers in usage insights:** left as they are _(human decision, 2026-10-29)_. Google's renderer calls our API like a browser; plan 014 doesn't filter it out.
- **Privacy:** no change. Crawlers fetch the same pages and API answers as visitors.

## Steps

2. **For you (team):**

1. Create the property at search.google.com/search-console, signed in with a team Google account (not a personal one, so access survives people leaving): choose **URL prefix**, enter `https://<domain>/<repo-name>/` (with the trailing slash), choose "HTML tag" and copy the `content` value into the Actions variable `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`. Don't click Verify until a release with the tag is live (step 4).
2. Set the Actions variable `NEXT_PUBLIC_SITE_ORIGIN` = `https://<domain>`.
3. Start a release (`hyperstim-release`) once the changes are merged.
4. In Search Console:
   - Click Verify.
   - Sitemaps: submit `https://<domain>/<repo-name>/sitemap.xml`.
   - URL Inspection: inspect the homepage, then "Request indexing". Do the same for rankings and how it works.
5. Add other team members under Settings → Users and permissions.
6. Check back after about a week: Pages (indexing) report, any errors in the sitemap report.

## Future improvements

To rank well rather than just be indexed:
- **Discoverable video and channel pages:** list dataset videos/channels in the sitemap, and give them real titles and descriptions. Today they are one static page filled in by the browser from `?id=`, so they all share one title. Doing it well means generating a page per video at build time, a bigger change for plans 004/005. Start with channels (hundreds, and what parents search for: "is <channel> overstimulating"); videos maybe never (tens of thousands, little unique text). Pages built with real data would also give AI crawlers and search engines our results, not just what the site is. Visitors would briefly see the numbers as of the release before the live ones, so it changes what people see: a decision of its own.
- **Structured data** (JSON-LD), e.g. `WebSite` and `Dataset`, so Google can show richer results.
- **Links from elsewhere:** the lab site, the paper, press, and the old site (a redirect from it when it is retired, 001 migration step 4). This matters more than any on-page change.
- **Bing Webmaster Tools:** import the property from Search Console; it also feeds DuckDuckGo and others.
- **Watch Search Console** for the queries people use, and adjust page wording to match.
- **Speed and accessibility checks** (Lighthouse) as part of release checks; Google uses page experience as a ranking signal.
